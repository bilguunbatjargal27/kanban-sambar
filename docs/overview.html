Fullstack interview · Kanban Sambar

What I built, and why it's built this way

A personal Kanban board: email/password auth, three columns, task CRUD with due date and label, drag-and-drop reordering saved to Postgres, search and filter, and a responsive layout. About 900 lines across 9 source files.

1 · Architecture

Three pieces, one direction of trust

The browser holds only a token. Every rule about who owns what is enforced on the server and in the database.

2 · What was built

Every requirement, and where it lives

🔐 Authentication

  • Register / login with email + password (6–72 chars)
  • Passwords stored as bcrypt hashes (cost 12)
  • 12-hour JWT. Logout removes it on that device
  • Duplicate email returns 409; wrong login returns 401

▦ Board

  • To Do In Progress Done
  • You only ever see your own tasks: every query filters by user_id
  • Another user's task returns 404, not 403, so you can't tell it exists

✏️ Task CRUD

  • Create (title, description, due date, label)
  • Edit in a modal, delete with confirm
  • Fixed labels: Bug Feature Improvement Urgent Research

↕️ Drag & drop

  • Move between columns and reorder within one
  • Saved with an integer position, so a refresh shows the same order
  • Works while filtered: hidden tasks keep their place

📱 Multi-device

  • The token isn't tied to a device, so you can log in on many at once
  • The board reloads when the window comes back into focus
  • Row locks stop two devices from scrambling the order

⭐ Extras

  • Due date: amber when due today, red when overdue
  • Search + label filter + due-date filter
  • Responsive: columns stack at 900px or less; touch drag; no iOS zoom on inputs
3 · Database

Two tables, rules enforced in the database too

The API validates first, and the database enforces the same rules again, so bad data can't get in even through code that skips the API.

How ordering works: each column is numbered 0, 1, 2, …. To move a card, the server locks both affected columns (SELECT … FOR UPDATE), takes the card out, inserts it at the new index, renumbers both columns from 0, and commits, all in one transaction.

Moving is its own endpoint rather than part of PUT because it changes other rows too (the whole column gets renumbered). Keeping it separate makes that side effect explicit.

6 · Tech stack

Why each piece, versus what else

FastAPIvs Django + DRF, Flask
WhyRequest and response types are Python type hints, which gives validation and Swagger docs for free. Little boilerplate, so the whole API is in one readable file.
vs othersDRF has a built-in admin and user model but needs serializers, viewsets and settings. Flask needs add-ons for validation and docs.
Trade-offNo admin panel, and no built-in migrations or auth: I wrote auth.py myself. For a large team app, Django's conventions scale better.
PostgreSQLvs MySQL, SQLite, MongoDB
WhyRequired by the brief, and the right fit: relational data (user → tasks), transactions, and SELECT … FOR UPDATE row locks for safe reordering.
vs othersSQLite allows only one writer at a time. MongoDB has no foreign keys or CHECK rules, so ownership would be enforced only in code.
Trade-offA server to run and set up. Overkill for a single user, but that's how production works.
SQLAlchemy 2vs raw SQL, Django ORM
WhyTyped models (Mapped[...]), parameterised queries (no SQL injection), and readable select() queries.
vs othersRaw SQL is faster to write once but easy to get wrong. The Django ORM only comes with Django.
Trade-offTables are created with create_all, with no migrations: I added the due date and label columns by hand with ALTER TABLE. Production would use Alembic.
React + Vitevs Vue, plain JS, Next.js
WhyA board is UI driven by state. With React, moving a card just updates the tasks array and the UI redraws to match. Vite gives instant hot reload while developing.
vs othersPlain JS + SortableJS is lighter but you update the page by hand. Next.js adds server rendering and routing we don't need.
Trade-offAbout 100 KB of JS (gzipped) and a Node toolchain. No TypeScript, to keep it light, so API shapes aren't type-checked.
@hello-pangea/dndvs dnd-kit, native HTML5 DnD
WhyBuilt specifically for lists and Kanban: smooth animations, touch and keyboard support, and it hands you source and destination indexes, which is exactly what /move needs.
vs othersdnd-kit is more flexible (grids, free placement) but needs more code. Native HTML5 drag-and-drop doesn't work on mobile.
Trade-offLists only, and nested scroll areas aren't supported well. That's why on mobile the columns stack and the whole page scrolls.
Plain CSSvs Tailwind, MUI
WhyOne 140-line file with colour variables. No build plugin, nothing extra to learn.
vs othersTailwind is faster for big UIs. MUI looks generic and is heavy.
Trade-offDoesn't scale to many screens without a component system.
7 · Key techniques

Decisions inside the code

DecisionChosenAlternativeWhy / trade-off
Password hashingbcrypt, cost 12Argon2id; SHA-256 (✗)Salted and deliberately slow. Argon2id is newer and also memory-hard, but bcrypt is battle-tested. Fast hashes like SHA-256 are unsafe for passwords.
SessionStateless JWT (HS256, 12 h)Server sessions + cookieNo session table, and multiple devices work for free. Cost: logout can't revoke a token, which stays valid until it expires.
Token storagelocalStoragehttpOnly cookieSimple, no CSRF handling. Cost: if a script is ever injected into the page (XSS), it can read the token. React escapes text by default, which reduces the risk.
OrderingInteger position, renumber on moveFractional keys / LexoRankEasy to reason about, and it never drifts. Cost: each move rewrites the whole column, fine for hundreds of cards. With fractional keys a move writes one row but needs occasional rebalancing.
ConcurrencyFOR UPDATE row locksVersion numbers (optimistic locking)Two devices moving at once can't create duplicate positions. Whoever commits last wins, and the UI then shows the server's order.
Multi-device syncReload on focusWebSocket pushVery little code. Cost: not live. Another device updates when you switch back to it, not instantly.
Search / filterIn the browserServer query paramsInstant, no extra requests, and the API already returns only your tasks. Cost: loads every task. With thousands of tasks this should move to the server.
Ownership errors404 for others' tasks403Doesn't reveal that the task ID exists.
LabelsFixed list (API Literal + DB CHECK)Labels table, many-to-manyConsistent colours and a simple filter. Cost: one label per task, and adding a label means changing the code.
8 · Honest gaps

What I'd fix before production

HIGH

Default JWT secret

SECRET_KEY falls back to "dev-secret-change-me". It must come from the environment in production.

HIGH

No rate limiting

Login can be brute-forced. Add per-IP and per-email limits.

MED

No token revocation

Use short access tokens plus refresh tokens, or a deny-list, for "log out everywhere".

MED

No migrations

Switch create_all + hand-written ALTERs to Alembic.

MED

No automated tests

Verified with curl scripts only. Next would be pytest for /move edge cases and auth isolation.

LOW

Loose CORS for LAN testing

Any host on port 5173 is allowed, so you can test from a phone. Lock it to the real domain when deployed.
